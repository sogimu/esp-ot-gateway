# REST API

[English](api.en.md) | **Русский**

Каждое действие веб-дашборда опирается на JSON-эндпоинт, так что всё, что умеет интерфейс, умеет и `curl`. Сам дашборд — эталонный клиент (он опрашивает устройство каждые 2 с): откройте его с DevTools браузера → Network и увидите живые формы запросов и ответов.

> ⚠️ **Заметка мейнтейнеру:** маршруты и имена полей с пометкой `TODO(verify)` восстановлены по поведению дашборда — сверьте их с HTTP-обработчиками перед публикацией.

Базовый URL: `http://<ip-устройства>`. Аутентификации нет — только для локальной сети (см. заметку о безопасности в [wifi-setup.md](wifi-setup.md)). Все ответы — JSON; POST-эндпоинты сохраняют настройки в NVS и переживают перезагрузку.

## `GET/POST /api/control`

Вкладка «Управление» отображается в эти поля. GET возвращает полное состояние; POST принимает любое подмножество:

| Поле | Тип / значения | Элемент UI |
|---|---|---|
| `ch_enable` | bool | Отопление → Разрешение |
| `ch_mode` | `manual` \| `pid` `TODO(verify значения)` | Режим: Ручной / Адаптивный (PID) |
| `ch_submode` | `static` \| `schedule` `TODO(verify значения)` | Подрежим: Статичный / По расписанию |
| `ch_setpoint` | °C, обрезается до границ котла (вкладка «Инфо»; 25–80 °C на проверенном Baxi) | Уставка CH (ручной + статичный) |
| `pid.sensor` | `t1` \| `t2` | комнатный датчик для PID |
| `pid.target` | °C | целевая комнатная температура (PID + статичный) |
| `pid.kp` / `pid.ki` / `pid.kd` | число `TODO(verify)` | коэффициенты PID |
| `dhw_enable` | bool | Бойлер БКН → Разрешение |
| `dhw_setpoint` | °C, обрезается до границ котла (35–60 °C на проверенном Baxi) | Уставка БКН |
| `dhw_hysteresis` | °C (напр., 2.0) | Гистерезис БКН |

Красная кнопка **«Выключить котёл»** — аварийная остановка: `TODO(verify): её эндпоинт/поле (например, POST /api/control {"boiler_off":true})`.

```bash
# Ручной статичный: отопление включено, уставка подачи 35 °C
curl -s -X POST http://192.168.0.37/api/control \
  -H 'Content-Type: application/json' \
  -d '{"ch_enable":true,"ch_mode":"manual","ch_submode":"static","ch_setpoint":35}'

# Адаптивный (PID) с суточным расписанием комнатных целей
curl -s -X POST http://192.168.0.37/api/control \
  -H 'Content-Type: application/json' \
  -d '{"ch_enable":true,"ch_mode":"pid","ch_submode":"schedule"}'
```

Значения вне диапазона обрезаются до границ котла из `/api/info`; некорректный JSON отклоняется и пишется в журнал событий.

## `GET/POST /api/schedule` — суточная сетка

Режим и подрежим ортогональны: сетка используется всегда, когда `ch_submode = schedule`, а её смысл следует за режимом:

- **Ручной + расписание** — каждое почасовое значение — это **уставка подачи отопления** на этот час;
- **PID + расписание** — каждое почасовое значение — это **целевая комнатная температура для PID** на этот час, и PID продолжает модулировать котёл, удерживая её.

Часы — в локальном времени устройства, поэтому должны быть настроены NTP и часовой пояс (состояние синхронизации — на вкладке «Инфо»; сама синхронизация видна в «Журнале»).

Ответ GET / тело POST `TODO(verify: точная форма)`:

```json
{
  "entries": [19, 19, 19, 19, 19, 20, 21, 22, 22, 21, 21, 21,
              21, 21, 21, 21, 22, 22, 22, 22, 22, 21, 20, 19]
}
```

`entries[0]` — 00:00–00:59, `entries[23]` — 23:00–23:59 (пример выше — комнатные цели PID с ночным снижением).

```bash
curl -s http://192.168.0.37/api/schedule | jq
curl -s -X POST http://192.168.0.37/api/schedule \
  -H 'Content-Type: application/json' \
  -d '{"entries":[19,19,19,19,19,20,21,22,22,21,21,21,21,21,21,21,22,22,22,22,22,21,20,19]}'
```

POST заменяет сетку целиком атомарно и сохраняет её в NVS.

## Виртуальный счётчик газа

Вкладка счётчика показывает — а API отражает `TODO(verify: маршруты)`:

- **Показания:** мгновенный расход (м³/ч), накопленный объём, средние за 1ч/3ч/12ч/24ч/7д, **погрешность оценки %**, текущий калибровочный коэффициент **K**.
- **Сверка:**
  - однократная установка начального показания («Нач. показание» → Установить);
  - ввод текущего показания физического счётчика («Показание счётчика» → Записать). Сверка принимается только после достаточного расхода с прошлой сверки (> 0.01 м³, и накопленный объём > 5% расхода — оба счётчика видны в UI);
  - каждая принятая сверка добавляет запись в журнал (время, факт, расчёт, Δ, %, K было, K стало) и обновляет сглаженный фильтром Калмана коэффициент K.
- **Сбросы:** сброс статистики газа; сброс журнала сверки и K.

```bash
curl -s http://192.168.0.37/api/gas | jq
curl -s -X POST http://192.168.0.37/api/gas/correction \
  -H 'Content-Type: application/json' -d '{"meter_reading_m3": 1382.041}'   # TODO(verify)
```

## `GET /api/info`

Зеркало вкладки «Инфо»: код ошибки OEM, флаги ASF, OEM-диагностика, сообщённые котлом границы уставок CH/DHW, версия ПО котла, версия OpenTherm, платформа, часовой пояс (смещение UTC, редактируется), NTP-серверы 1/2 (редактируются), время ESP32, время работы.

## Data-ID OpenTherm

Значения, которыми шлюз обменивается с котлом по протоколу OpenTherm. R/W выведено из использования в прошивке: **R** — шлюз опрашивает (read), **W** — шлюз записывает (write). Именно эти Data-ID стоят за полями `/api/status`, `/api/stats` и `/api/info`.

| ID | Назначение | R/W | Примечание |
|---|---|---|---|
| 0 | STATUS (флаги статуса) | R/W | Мастер пишет свои флаги (CH/DHW/CH2 enable), котёл возвращает свои (авария, горелка, пламя, ГВС) |
| 1 | Уставка подачи CH | W | |
| 2 | Конфигурация мастера | W | |
| 3 | Конфигурация котла | R | |
| 5 | Флаги аварий ASF | R | HB = флаги, LB = OEM-код |
| 8 | Уставка CH2 | W | Используется для БКН на системных котлах |
| 17 | Модуляция, % | R | |
| 18 | Давление CH | R | |
| 25 | Температура подачи CH | R | |
| 26 | Температура ГВС (БКН) | R | |
| 27 | Уличная температура | R | |
| 28 | Температура обратки | R | |
| 48 | Границы уставки ГВС | R | lo/hi байты |
| 49 | Границы уставки CH | R | lo/hi байты |
| 56 | Уставка ГВС (DHW setpoint) | R | По спецификации ID записываемый, но проверенный Baxi запись отклоняет — см. примечание ниже |
| 57 | Макс. уставка CH | W | |
| 115 | OEM-диагностика | R | |
| 116 | Счётчик запусков горелки | R | |
| 117 | Счётчик запусков насоса CH | R | |
| 118 | Счётчик переключений 3-ход. клапана | R | |
| 119 | Счётчик запусков горелки ГВС | R | |
| 120 | Наработка горелки, ч | R | |
| 121 | Наработка насоса CH, ч | R | |
| 122 | Наработка клапана ГВС, ч | R | |
| 123 | Наработка горелки ГВС, ч | R | |
| 124 | Версия протокола OT (котёл) | R | |
| 125 | Версия ПО котла | R | |
| 126 | Версия ПО мастера | W | |

> ⚠️ **ID 56 (уставка ГВС).** По спецификации OpenTherm это записываемый параметр, но на проверенном котле **Baxi Duo-tec Compact** запись отклоняется (ответ NO_RESP / `DATA_INVALID`), и котёл удерживает собственную внутреннюю уставку (~60 °C с передней панели). Поэтому в таблице ID 56 помечен как **R** (фактически только чтение). Не рассчитывайте на успешную запись ID 56; регулирование ГВС шлюз выполняет через флаг `DHW_ENABLE` в STATUS (ID 0) с гистерезисом — уставку `dhw_setpoint` в `/api/control` шлюз отрабатывает сам.

## `GET /api/log`

Журнал на 256 записей с теми же категориями, что и фильтры в UI: система, пользователь, оборудование, режимы, запуск. Метки времени до первой синхронизации SNTP показываются как неизвестные (`??:??:??`) — порядок записей при этом сохраняется.

## MQTT

```bash
curl -s http://192.168.0.37/api/mqtt/status | jq

curl -s -X POST http://192.168.0.37/api/mqtt/settings \
  -H 'Content-Type: application/json' \
  -d '{"enabled":true,"host":"192.168.0.67","port":1883,"username":"user","password":"secret",
       "prefix":"esp-ot-gateway","status_interval_s":15,"stats_interval_s":30,"tls":false}'
```

Настройки соответствуют вкладке MQTT: главный выключатель, сервер, порт, логин, пароль, префикс топиков, интервал статуса (с), интервал статистики (с), переключатель TLS. Справочник топиков и детали Home Assistant: [mqtt.md](mqtt.md).

## Соглашения

- Ошибки возвращают статус, отличный от 2xx, с телом `{"error":"..."}` `TODO(verify)`.
- Числовые уставки обрезаются до границ, сообщённых котлом, а не отклоняются за небольшой выход за диапазон.
- Дашборд опрашивает устройство каждые **2 с** (видно на вкладке «Инфо») — считайте это разумным минимумом периода опроса; устройство — микроконтроллер на 240 МГц, который параллельно «дёргает ногами» OpenTherm.
