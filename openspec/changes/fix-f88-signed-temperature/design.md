## Context

OpenTherm передаёт температуры в знаковом формате f8.8: старший байт — знаковая целая часть (two's complement `int8_t`), младший — дробная (1/256). Пример: `-2.0°C` → `0xFE00`.

Сейчас `BoilerOpenThermAdapter::read()` декодирует сырое значение беззнаково:

```cpp
r.value_f88 = static_cast<float>(resp.data_value) / 256.0f;
```

Для `0xFE00` (= 65024) это даёт `254.0` вместо `-2.0`. Отсюда «Улица 254°C» при реальных 0/-2°C.

Ключевая тонкость: `read()` используется не только для температур, но и как «переносчик» сырого значения для байт-парных ID (ASF-флаги, версия, bounds, runtime-счётчики). Эти вызывающие стороны восстанавливают `uint16_t` обратно через `float_to_f88(r.value_f88)`. Поэтому нельзя просто сделать `read()` знаковым — это сломает round-trip для значений со старшим битом (например, ASF-флаги 0x80…).

Корректный декодер уже существует: `OT_f88_to_float()` в `main/c_legacy/opentherm.c:226` (целая часть как `int8_t`), но адаптер его не использует.

## Goals / Non-Goals

**Goals:**
- Температурные ID (подача 25, бойлер 26, улица 27, обратка 28) декодируются знаково, отрицательные значения корректны.
- Сохранить беззнаковое поведение для байт-парных ID (round-trip) и модуляции.
- Покрыть декодирование тестами (отрицательные, дробные, границы).

**Non-Goals:**
- Не менять `float_to_f88` для поддержки отрицательных записей (сетпоинты всегда положительны).
- Не трогать существующий round-trip runtime-счётчиков (отдельная известная слабость точности float при >255.99 — вне scope).
- Не менять формат MQTT/web — меняется только значение температуры на входе.

## Decisions

### Decision 1: отдельный знаковый путь чтения температуры

Добавить в `IBoilerHardware` метод `read_temperature(uint8_t data_id)`, возвращающий знаковый f8.8-float. Не перегружать `read()`.

- **Почему:** `read()` уже перегружен семантически (float-температура и raw-carrier для round-trip). Отдельный метод разграничивает «знаковое значение» и «сырой переносчик» без риска сломать байт-парные ID.
- **Альтернатива (отклонена):** сделать `read()` знаковым и чинить `float_to_f88` для отрицательных — ломает round-trip ASF-флагов/версии со старшим битом и создаёт неявную связь.

### Decision 2: переиспользовать `OT_f88_to_float`

Реализовать `read_temperature()` через уже существующий `OT_f88_to_float(resp.data_value)`. Адаптер уже включает `c_legacy/opentherm.h`.

- **Почему:** один источник истины для f8.8-декодирования; не плодить дубликаты.
- **Альтернатива (отклонена):** свой C++-декодер `int8_t(v>>8) + (v&0xFF)/256.0f` — дублирует логику, риск рассинхрона.

### Decision 3: переключить 4 температурных call-site

В `boiler_poll_interactor.cpp` заменить `boiler_.read(...)` на `boiler_.read_temperature(...)` для ID 25, 26, 27, 28. Остальные (`modulation`, byte-pair, counters) оставить на `read()`.

### Decision 4: убрать мёртвый дубликат

`BoilerPollInteractor::f88_to_float()` (беззнаковое деление) нигде не вызывается — удалить метод и его объявление в заголовке, чтобы не оставалось источника той же ошибки.

## Risks / Trade-offs

- [Изменение интерфейса `IBoilerHardware` требует обновить `FakeBoilerHardware` в `test/fakes/`] → добавить реализацию `read_temperature()` в фейк (по умолчанию знаковый декодер или конфигурируемое значение).
- [Кто-то мог опираться на старое (некорректное) значение 254°C как на «нет датчика»] → проверка: в коде нет такой логики; корректность важнее обратной совместимости с багом.
- [Дробная точность f8.8 ограничена 1/256 ≈ 0.004°C] → достаточно для отображения (1 знак после запятой) и газовой коррекции.
- [Возможен иной source-of-truth в C legacy] → `OT_f88_to_float` уже используется в `opentherm.c` и даёт эталонное поведение; тесты сверяются с ним.

## Migration Plan

1. Добавить `read_temperature()` в интерфейс, адаптер и фейк.
2. Переключить 4 call-site температур.
3. Удалить мёртвый `f88_to_float`.
4. Собрать и прогнать unit-тесты (плюс новый тест декодирования).
5. На устройстве: убедиться, что «Улица» при отрицательной температуре показывает отрицательное значение, а не ~254.

Откат: возврат на `read()` для четырёх call-site (единичный revert), интерфейсный метод безвреден.

## Open Questions

- Нужно ли добавлять «не-число»/плейсхолдер для ID 27, когда датчик физически отсутствует (котёл может возвращать 0x7FFF = «неизвестно»)? Сейчас газовый корректор опирается на `outdoor_temp_valid_` и 6-часовой таймаут. Вероятно, отдельный change.
