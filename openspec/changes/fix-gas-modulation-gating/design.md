## Context

`GasFlowService::execute()` (gas_flow_estimator.cpp:117–160) использует флаг `flame` как сигнал «горелка горит»: при `flame=true` считает `flow = k × power/cv × warmup` и интегрирует объём. Бит `flame` читается из OpenTherm STATUS (ID=0, LB бит 3).

На стенде (Baxi Duo-tec Compact 1.24) зафиксировано: в простое отопления (`ch_temp` выше уставки, БКН удовлетворён) устройство длительно отдаёт `flame=1, modulation=0`, при этом газовый счётчик СГМБ-4 стоит на месте (нулевое потребление). Виртуальный интеграл при этом растёт со скоростью `k × pmin / cv ≈ 0.22 м³/ч`. Гистограмма модуляции по времени «flame-on»: p25=0, p50=28, p75=p90=p99=48 — то есть четверть времени `flame=1` приходится на `mod=0` (фантом), а реальное горение даёт 28–48%.

Вывод: на этом котле `modulation=0` ↔ горелка не горит, `modulation>0` ↔ горит. Гейтить нужно по модуляции, а не по flame.

## Goals / Non-Goals

**Goals:**

- Накопление расхода происходит только когда модуляция > 0.
- Фильтр Калмана модуляции не «прилипает» между горениями.
- Поведение остальных сервисов (BurnCycle/ModulationStats/DHWPredict), завязанных на `flame`, не меняется.

**Non-Goals:**

- Изменение кривой мощности (`calc_power`), `pmin/pmax`, `k_calib`.
- Удаление поля `flame` из состояния (нужно другим сервисам и отображению).

## Decisions

### 1. Сигнал «горит» — сырая модуляция > ε

В `execute()` вычисляем `bool firing = (mod_raw > FIRING_EPS)` (ε = 0.5%) и используем его вместо `flame`:

```
if (firing) { ... calc flow, integrate ... } else { latest_flow_ = 0; }
```

Порог ε защищает от шума float; реальное горение на этом котле 28–48%, так что 0.5% не отсечёт полезный сигнал.

**Альтернатива:** `flame && (mod>0)` — отклонена: `flame` врёт (всегда 1 в простое), поэтому условия вырождается в `mod>0`, а лишняя зависимость от ненадёжного бита не нужна. **Альтернатива:** `mod ≥ 1%` — отклонена: менее прозрачно, а ε=0.5 покрывает тот же смысл.

### 2. Сброс Калмана на переходе 0 → >0

`Kalman1D kalman_mod_{0, 0.1, 1.0}` копил состояние между циклами (обновлялся только при flame). При новом горении фильтр стартовал бы с устаревшего значения и временно завышал мощность. На переходе `!firing_prev_ && firing` сбрасываем `kalman_mod_.reset(mod_raw)` и `ignition_start_ms_ = now_ms` (для warmup-фактора).

### 3. `flame` остаётся в состоянии, но GasFlowService его не читает

`flame` по-прежнему пишется в `HeatingState` и используется `BurnCycleService` (подсчёт циклов), `ModulationStatsService` (гейт сэмплирования), `DHWPredictService` (сессии ГВС). Меняем только `GasFlowService`.

## Risks / Trade-offs

- **[Котёл с честным отчётом «mod=0 на минимальном горении» станет недосчитывать]** → Для целевого Baxi это не так (mod=0 = выключен); ε мала. Отмечено как предположение под конкретный котёл.
- **[Сброс Калмана даёт небольшой переходный процесс]** → Компенсируется warmup-фактором 0.85→1.0 на первые 60 с.
- **[`mod_raw` может дёргаться вблизи порога]** → ε=0.5% и фильтр сглаживают; гистерезиса не вводим (не требуется).

## Migration Plan

Изменение только логики оценки расхода; NVS-форматы не меняются, миграции нет. Откат — возврат flame-гейта в `execute()`. После прошивки журнал сверки продолжит корректировать `k_calib`.
