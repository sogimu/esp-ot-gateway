## Context

`promote.yml` выбирает старший rc, достижимый из head PR (`git tag --merged HEAD_SHA ... | sort -V | tail -1`), создаёт стабильный тег на merge-коммите и запускает `tests.yml` через `workflow_dispatch` с `source_rc=$RC`. Шаг «Publish GitHub Release» в `tests.yml` при создании нового стабильного релиза удаляет ровно этот `source_rc`. Промежуточные rc той же версии (например `v0.8.1-rc1` при промоушене `v0.8.1-rc2`) остаются навсегда — в релизах, в `versions.json` и в секции «Тестовые» веб-флашера.

## Goals / Non-Goals

**Goals:**

- Автоматически удалять все тестовые релизы и теги той же версии при промоушене в стабильную.
- Не трогать rc других версий.
- Сохранить существующее поведение: при уже существующем стабильном теге/релизе уборки нет.

**Non-Goals:**

- Ретроактивная чистка уже осиротевших тегов (текущий `v0.8.1-rc1` этим изменением не удалится).
- Изменение выбора промоутируемого rc (по-прежнему старший).
- Уборка rc в других сценариях (например, ручной push стабильного тега без `source_rc`).

## Decisions

### 1. Список соседей выводится из стабильного тега внутри релизного прогона

В ветке создания нового стабильного релиза вместо удаления одного `SOURCE_RC` перебираем удалённые теги по префиксу стабильного тега:

```
git ls-remote --tags origin "refs/tags/${TAG}-rc*"
```

с фильтром `^${TAG}-rc[0-9]+$`, и для каждого тега удаляем релиз (`gh release delete --yes`, best-effort) и сам тег (`git push origin ":refs/tags/<rc>"`, best-effort). `SOURCE_RC` сохраняется только как признак «стабильный релиз создан из промоушена».

**Альтернатива:** передавать список rc из `promote.yml` через `workflow_dispatch`-инпут — отклонена: инпуты строковые, а релизный прогон и так знает стабильный `$TAG` и может вывести соседей сам. **Альтернатива:** `git tag -l` локально — отклонена: `actions/checkout` не гарантирует загрузку всех тегов; `git ls-remote` спрашивает удалённый репозиторий напрямую.

### 2. Уборка остаётся gated на создание нового релиза и на непустой `SOURCE_RC`

Уборка выполняется только внутри ветки, где стабильный релиз создаётся впервые, и только при `-n "$SOURCE_RC"`. Это сохраняет сценарий «стабильный тег уже есть → тестовые теги остаются» и не удаляет соседей, если стабильный тег был запушен вручную без промоушена.

## Risks / Trade-offs

- **[Удаляется незавершённый rc той же версии]** → Приемлемо: та же версия уже выпущена стабильно, а теги других версий не затрагиваются.
- **[Сбой листинга/удаления тега]** → Best-effort (`|| true`), как и текущая уборка одного тега: релиз уже создан, сбой уборки не должен ронять прогон.
- **[Ошибка фильтрации в шелле]** → Строгий regex `^${TAG}-rc[0-9]+$`; перечисление через `git ls-remote`, а не локальные теги.

## Migration Plan

Изменение только в GitHub Actions. Вступает в силу со следующего релизного прогона; миграции данных нет. Уже осиротевшие теги (текущий `v0.8.1-rc1`) ретроактивно не чистятся — при желании удаляются вручную.
