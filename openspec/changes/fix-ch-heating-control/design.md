# Design: fix-ch-heating-control

## Context

Шлюз — это OpenTherm-мастер для котла Baxi Duo-tec Compact. Сегодня в ручном режиме он шлёт `CH_ENABLE=1` + уставку подачи (ID 1), а котёл сам модулирует горелку и управляет насосом. Это даёт три дефекта:

1. Уставки обрезаются по захардкоженным константам `[20,80]` (CH) и `[35,65]/[35,80]` (DHW), разбросанным по HTTP-обработчику и use case. Реальные границы котла (`ID 49` CH, `ID 48` DHW) уже читаются в `boiler_poll_interactor.cpp` и хранятся как `ch_sp_min/max`, `dhw_sp_min/max`, но используются только для UI-слайдера и PID-диапазона.
2. Обещанный в UI «Гистерезис CH» не реализован: `pid_poll_interactor.cpp` никогда не пишет `set_ch_enable(false)`, флаг `pid_ch_enabled` — индикаторный. Ручной режим вообще не имеет гистерезиса — котёл не останавливает насос между циклами.
3. При рукопожатии `ID 2` (Master Configuration) заполняется эхом `ID 3` (Slave Configuration): биты этих Data-ID имеют разный смысл (в ID 2 bit 0 = Smart Power, в ID 3 bit 0 = DHW present), а Member ID мастера подменяется Member ID котла.

Гистерезис ГВС уже реализован корректно (`DHWHysteresisService` + `do_dhw_hysteresis()`): `dhw_enable` — мастер-разрешение, а `dhw_priority` (результат гистерезиса) реально управляет битом `DHW_ENABLE`. Этот паттерн — образец для CH.

## Goals / Non-Goals

**Goals:**
- Один источник истины для границ уставок (ID 49/48), единая обрезка во всех точках входа, не шире, чем поддерживает котёл.
- Реализовать CH-гистерезис по температуре подачи в ручном режиме: снятие/поднятие `CH_ENABLE` так, чтобы котёл гасил горелку и останавливал насос (с выбегом) между циклами.
- Исправить запись `ID 2` при рукопожатии.

**Non-Goals:**
- Не меняем PID-режим (его комнатный гистерезис/выключение насоса — отдельная задача).
- Не добавляем прямой команды управления насосом/горелкой (в OpenTherm их нет).
- Не трогаем газовую модель и прочие подсистемы.

## Decisions

### D1. Единая обрезка в use case, а не в драйверах

Обрезку уставок переносим в `SystemConfigInteractor` (единственный «шлюз» записи конфигурации). HTTP/MQTT/расписание только парсят значения и вызывают сеттер, без собственных констант.

- Добавляем приватные `clamp_ch(float)` / `clamp_dhw(float)`, которые под `lock_shared()` читают `get_ch_sp_min/max`, `get_dhw_sp_min/max` и обрезают.
- Если границы ещё не валидны (`max <= min` — котёл не ответил на ID 49/48), используем консервативные fallback-константы: CH `[25,80]`, DHW `[35,60]` (совпадают с документированным Baxi). Fallback живёт только первые ~30 с после старта, пока не отработают шаги 15/16 опроса.

*Альтернатива:* обрезать в каждом драйвере отдельно — отвергнуто, дублирует источник истины и расходится (уже сейчас CH `[20,80]` в HTTP против `[35,80]` в use case для DHW).

### D2. CH-гистерезис по образцу DHW

Вводим `CHHysteresisService` (чистые функции `should_heat(flow, setpoint, hyst)` / `should_stop(flow, setpoint)`), зеркалящий `DHWHysteresisService`.

- Новое конфигурируемое поле `ch_hysteresis` (°C), NVS-персистентно, **по умолчанию 0 = выключено** (сохраняем текущее модулирующее поведение для тех, кто его хочет). `> 0` включает bang-bang в ручном режиме.
- В `BoilerPollInteractor` добавляем `do_ch_hysteresis()`, запускаемый каждый цикл (как `do_dhw_hysteresis()`), и локальный флаг `ch_hysteresis_on_`.
- `build_master_byte()` вычисляет: `ch_on = ch_enable && (ch_hysteresis == 0 || ch_hysteresis_on_)`. При выключенном гистерезисе поведение идентично текущему.
- Уставка подачи продолжает писаться как раньше; при поднятом `CH_ENABLE` котёл греет до неё.

*Альтернатива:* гистерезис по комнатной температуре — отвергнуто для ручного режима: ручной режим оперирует уставкой подачи, и «штатное» поведение котла — это удержание подачи.

### D3. ID 2 при рукопожатии — оставляем эхо (workaround Baxi)

Первоначально планировали писать в ID 2 собственную конфигурацию мастера (`0x003F`), но это сломало DHW-управление на Baxi Duo-tec Compact (клапан не переключался на БКН, аномальная модуляция CH). Поэтому сохраняем исходное поведение: `do_handshake()` (и legacy `ot_handshake()`) пишет в ID 2 эхо Slave Configuration (ID 3). Это эмпирический workaround, задокументированный в `docs/api.md`.

### D4. Границы читаются как есть (без расширения скоупа)

`ID 49/48` — это пара байтов, а не f8.8. Существующий round-trip через `value_f88`/`float_to_f88` для 16-бит точен, поэтому оставляем его как есть; отдельный `read_raw()` для байтовых ID не вводим в этом change (фиксируется только в комментарии, чтобы будущая правка не сломала чтение bounds).

## Risks / Trade-offs

- **Bang-bang по подаче даёт «среднюю» подачу у уставки, а не ровную полку** → горелка всё равно перегревает из-за нижнего порога 3.4 кВт, но насос теперь встаёт между циклами (это и есть цель). → Mitigation: гистерезис конфигурируем, документировать ограничение.
- **Частое переключение `CH_ENABLE`** — формально не «штатный» способ для модулирующего мастера, но поддерживается котлом (он сам описывает выбег «if the ambient thermostat causes the burner to go out»). → Mitigation: гистерезис > 0 уменьшает частоту; по умолчанию выключен.
- **Fallback-границы могут не совпадать с другим котлом** → Mitigation: fallback используется только до первого чтения ID 49/48; после этого — всегда реальные границы.
- **Изменение обрезки может изменить видимое поведение сохранённых уставок** (например, сохранённые 20 °C теперь станут 25 °C) → Mitigation: пересчёт при загрузке из NVS не требуется — обрезка применяется при записи, а при выводе состояние уже в диапазоне.

## Migration Plan

1. Слить обрезку в `SystemConfigInteractor`, убрать константы из HTTP/расписания.
2. Добавить `ch_hysteresis` в состояние + NVS + UI (поле в разделе «Управление»).
3. Добавить `CHHysteresisService` + `do_ch_hysteresis()` + правку `build_master_byte()`.
4. Исправить запись ID 2.
5. Обновить `docs/api.md` (диапазоны, новое поле `ch_hysteresis`).

Откат: `ch_hysteresis=0` возвращает прежнее модулирующее поведение; правки обрезки/ID 2 обратимы отдельными коммитами.

## Open Questions

- Нужен ли отдельный UI-тумблер для CH-гистерезиса или достаточно числового поля (0 = выкл)? Пока выбран вариант «числовое поле, 0 = выкл».
- Сохранять ли флаги `ID 3` (DHW present, storage tank, CH2) в состоянии для будущей логики — вне скоупа этого change.
