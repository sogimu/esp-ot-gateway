# Design: fix-ch-heating-control

## Context

Шлюз — это OpenTherm-мастер для котла Baxi Duo-tec Compact. Уставки CH/DHW обрезались по захардкоженным константам `[20,80]` (CH) и `[35,65]/[35,80]` (DHW), разбросанным по HTTP-обработчику и use case. Реальные границы котла (`ID 49` CH, `ID 48` DHW) уже читаются в `boiler_poll_interactor.cpp` и хранятся как `ch_sp_min/max`, `dhw_sp_min/max`, но использовались только для UI-слайдера и PID-диапазона. В итоге можно было, например, задать DHW-уставку 80 °C при реальном максимуме котла 60 °C.

## Goals / Non-Goals

**Goals:**
- Один источник истины для границ уставок (ID 49/48), единая обрезка во всех точках входа, не шире, чем поддерживает котёл.
- Переобжим CH-уставки на пути записи в котёл (симметрично DHW).

**Non-Goals:**
- Не добавляем гистерезис отопления (комнатный on/off-термостат — отдельный будущий change).
- Не меняем Master Configuration (ID 2) — оставляем эхо slave-конфига как workaround для Baxi.
- Не трогаем газовую модель и прочие подсистемы.

## Decisions

### D1. Единая обрезка в use case, а не в драйверах

Обрезку уставок переносим в `SystemConfigInteractor` (единственный «шлюз» записи конфигурации). HTTP/MQTT/расписание только парсят значения и вызывают сеттер, без собственных констант.

- Добавляем приватные `clamp_ch(float)` / `clamp_dhw(float)`, которые под `lock_shared()` читают `get_ch_sp_min/max`, `get_dhw_sp_min/max` и обрезают.
- Если границы ещё не валидны (`lo <= 0` или `hi <= lo` — котёл не ответил на ID 49/48), используем консервативные fallback-константы: CH `[25,80]`, DHW `[35,60]` (совпадают с документированным Baxi). Fallback живёт только первые ~30 с после старта, пока не отработают шаги 15/16 опроса.

*Альтернатива:* обрезать в каждом драйвере отдельно — отвергнуто, дублирует источник истины и расходится (уже сейчас CH `[20,80]` в HTTP против `[35,80]` в use case для DHW).

### D2. Переобжим CH-уставки на пути записи

В `do_extra_step()` (шаги 1/10) при записи `OT_ID_CH_SETPOINT` дополнительно обрезаем значение по верхней границе котла (`get_ch_sp_max()`), симметрично существующему поведению DHW (шаги 3/11). Это защищает от значений, загруженных из NVS или записанных другими путями в обход сеттера.

### D3. Границы читаются как есть (без расширения скоупа)

`ID 49/48` — это пара байтов, а не f8.8. Существующий round-trip через `value_f88`/`float_to_f88` для 16-бит точен, поэтому оставляем его как есть; отдельный `read_raw()` для байтовых ID не вводим в этом change.

## Risks / Trade-offs

- **Fallback-границы могут не совпадать с другим котлом** → Mitigation: fallback используется только до первого чтения ID 49/48; после этого — всегда реальные границы.
- **Изменение обрезки может изменить видимое поведение сохранённых уставок** (например, DHW-уставка 65–80 °C теперь станет 60 °C) → Mitigation: это и есть цель — привести диапазон к реальному максимуму котла; обрезка применяется при записи.

## Migration Plan

1. Слить обрезку в `SystemConfigInteractor`, убрать константы из HTTP/MQTT/расписания.
2. Добавить переобжим CH-уставки по `ch_sp_max` в `boiler_poll_interactor.cpp` (шаги 1/10).
3. Обновить `docs/api.md` / `docs/api.en.md`.
