## Context

`PidPollInteractor` управляет адаптивным режимом СО. Цель комнаты (`pid_target_room`) задаётся через `/api/config` (`set_pid_parameters` → `set_pid_config`) и хранится в NVS (`boiler_nvs_store.cpp`, ключ `pid_trg`). `SystemConfigInteractor::set_ch_mode()` при ручных режимах вызывает `pid_poll_->disable()`, при адаптивных — `enable()`.

Причина бага: `disable()` вызывает `set_pid_state(false, false, 0, 0, 0, 0, 0, 0, false, 0, false)` — седьмой (комнатная температура) и восьмой (цель) аргументы равны 0. Выключенная ветка `execute()` делает то же на каждом poll. `enable()` читает текущую цель — уже 0. `set_pid_enable()` (явный тумблер PID) цель сохраняет, поэтому путь смены режима ведёт себя несогласованно.

`set_ch_mode()` сохраняет конфиг в NVS **до** `disable()`, поэтому в NVS остаётся старая цель, а в state/UI — 0; следующее сохранение конфига записывает 0.

## Goals / Non-Goals

**Goals:**
- Цель комнаты переживает цикл Manual ↔ Adaptive и выключенные poll-циклы.
- Последняя измеренная комнатная температура не обнуляется при выключении PID.
- Регрессионные тесты на оба пути.
- Поведение согласовано с `set_pid_enable()`.

**Non-Goals:**
- Изменение алгоритма PID, семантики режимов, формата NVS или UI.
- Цель расписания (`PID_Sched`) — она по-прежнему берётся из расписания.

## Decisions

1. **Сохранять `pid_room_temp` и `pid_target_room` в `disable()` и в выключенной ветке `execute()`**, передавая `get_pid_room_temp()` / `get_pid_target_room()` вместо 0. Цель — пользовательская настройка, комнатная температура — последнее измерение; обнулять их при остановке контроллера не нужно. Остальные поля (output/P/I/D, active, cycle lock, lockout) сбрасываются как раньше.
   - Альтернатива: обнулять комнатную температуру, сохраняя только цель — несогласованно с отображением; последнее значение безвредно.
2. **Читать значения до `lock_exclusive()`**, как уже делается для `was_enabled`, чтобы не менять порядок блокировок.
3. **`enable()` и `set_pid_enable()` не трогать** — они уже сохраняют цель; правим только два пути обнуления.
4. **Тесты на уровне `PidPollInteractor`**: `disable()` → `enable()` сохраняет цель; выключенный `execute()` сохраняет цель и комнатную температуру. Тест `SystemConfigInteractor` не нужен — он лишь делегирует в `disable()`.
5. **Без миграции NVS**: в NVS уже лежит корректная цель; фикс прекращает затирать runtime, следующее сохранение запишет правильное значение.

## Risks / Trade-offs

- **Устаревшая комнатная температура в UI при выключенном PID** → это последнее измерение; отдельные датчики T1/T2 в UI остаются живыми. Приемлемо.
- **`PID_Sched`**: цель обновляется из расписания каждый poll; сохранение в выключенном состоянии не мешает.
- **Существующие тесты**, ожидающие 0 после `disable()`, нужно проверить и обновить при необходимости.

## Migration Plan

Прошивка обновляется как обычно; данные NVS не меняются. Если в runtime цель уже 0 — после обновления её нужно один раз задать заново (в NVS может остаться старое значение, оно восстановится при загрузке). Откат — возврат коммита.
