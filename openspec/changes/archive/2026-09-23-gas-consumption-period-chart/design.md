## Context

Сейчас график расхода газа на вкладке «Виртуальный счётчик газа» показывает последнюю неделю с суточной гранулярностью. Данные собираются в `GasFlowService` (суточный аккумулятор + кольцо `daily_[8]`), сериализуются в `render_stats()` (`web_presenter_adapter.cpp:344`) и рисуются в `drawGasChart()` (`web_page.h:1419`) простыми SVG-барами без выбора периода, тултипа и итога.

Ограничения текущего решения: только сутки (нет почасовых данных для «сегодня/вчера»), глубина 8 дней, blob пишется в NVS целиком каждые ~10 мин.

Нужно: почасовой и двухмесячный учёт, выбор из 6 фиксированных диапазонов, стиль DeepSeek (итог за период + нативный тултип). Единицы — только м³. Миграция старой недельной истории не требуется (можно затереть).

## Goals / Non-Goals

**Goals:**
- Собирать почасовой (48 ч) и суточный (64 дня) расход газа, переживающий перезагрузку.
- Бережная запись в NVS: частый маленький blob «today+текущий час», редкий большой blob «история».
- UI: ComboBox на 6 диапазонов, бары в стиле DeepSeek, итог за период, нативный тултип.
- Не раздувать MQTT-топик `/stats`.

**Non-Goals:**
- Пересчёт расхода в деньги (цену газа не храним).
- Ручной выбор дат/времени.
- Миграция старых недельных данных (затираем).
- Экспорт/выгрузка истории.

## Decisions

### D1. Данные: два кольца в `GasFlowService`
- `hourly_[48]` с ключом `epoch_hour` (сегодня + вчера), пополняется на границе часа.
- `daily_[64]` с ключом `epoch_day`, пополняется на границе суток.
- Почасовой аккумулятор `hourly_accumulator_` работает параллельно суточному, оба не сбрасываются коррекциями счётчика (как и сейчас для суточного).

Альтернатива: отдельные массивы `today[24]`+`yesterday[24]` — проще читать, но ломаются при переводе часов/смене tz. Выбран кольцевой вариант по `epoch_hour`, пропущенные часы зануляются.

### D2. Агрегация диапазонов — на фронте, по ключам от сервера
Сервер отдаёт сырые данные с ключами:
- daily: `{ "epoch_day": N, "ym": Y*12+M, "d": "dd.mm", "m3": x, "today": 0|1 }`
- hourly: `{ "epoch_hour": N, "h": "HH", "m3": x }`

Фронт режет сам: «последние N дней» — последние N записей (данные уже отсортированы oldest→newest и заканчиваются сегодня); «этот/прошлый месяц» — фильтр по `ym` (берётся от записи `today`), т.е. без календарной логики и зависимости от tz браузера. «сегодня/вчера по часам» — из `hourly` по `epoch_day`.

Альтернатива: сервер считает все 6 готовых массивов — надёжнее по tz, но жирнее JSON и пересчёт на каждый опрос. Выбран фронт-слайсинг, т.к. сервер уже даёт корректные локальные `ym`/`epoch_*`, а данные крошечные.

### D3. Отдельный эндпоинт `/api/gas-history`
`render_stats()` используют и HTTP (`/api/stats`), и MQTT (`publish_stats`, `mqtt_interactor.cpp:428`). Раздувать его двухмесячной историей — плохо для MQTT-топика (публикуется каждые ~300 с). Поэтому:
- Новый метод `WebPresenterAdapter::render_gas_history(buf, size)`.
- Новый маршрут `GET /api/gas-history` со своим буфером (≥ 8 КБ).
- `render_stats()` и MQTT остаются без изменений.
- Веб-страница заводит отдельный `pollGasHistory()` (кадрирование ~10–60 с) и больше не рисует график из `/api/stats`.

Альтернатива: впихнуть историю в `/api/stats` (буфер 6144 байт тесен, MQTT раздувается). Отклонено.

### D4. NVS: раздельная персистентность (бережный подход)
- Ключ `today` (частый, каждые ~10 мин, ~124 Б): `today_epoch_day`, `today_m3`, `today_hours[24]` (завершённые часы сегодня), `current_hour`, `current_hour_m3`.
- Ключ `history` (редкий, на границе суток + при выключении, ~872 Б): `daily_[64]` (64 × 12 Б), `yesterday_hours[24]` (24 × 4 Б), `yesterday_epoch_day`.

Так частые записи остаются ~того же размера, что сейчас (~108 Б), а большой blob пишется раз в сутки — износ флеша практически не растёт. При ребуте восстанавливается «сегодня по часам» (из `today`) и «вчера + дни» (из `history`).

Структуры: `GasDailyBlob` (8 дней) заменяется на `GasTodayBlob` и `GasHistoryBlob` в `igas_correction_store.h`; соответствующие методы `load/save_daily_gas` заменяются на пару `load/save_today_gas` + `load/save_history_gas`.

### D5. Время и календарь
- `epoch_day = local_now / 86400`, `epoch_hour = local_now / 3600` (как сейчас для суток).
- `ym` и подписи «dd.mm»/«HH» считаются сервером через уже существующий `civil_from_seconds` (`web_presenter_adapter.cpp:25`).

## Risks / Trade-offs

- **Износ NVS** → частый blob ~124 Б сопоставим с текущим; большой пишется раз в сутки. Риск низкий.
- **Прыжки часов (NTP/tz/DST)** → часовая логика зануляет пропущенные часы; дублированный час просто досчитывается в тот же bucket (приемлемо). Сутки уже ведут себя аналогично.
- **Потеря данных при сбое питания** → «today» теряет ≤ 1 интервал персистентности (~10 мин) текущего часа; история не страдает.
- **Размер `/api/gas-history`** → ~112 записей ≈ 3–4 КБ, отдельный буфер 8 КБ; HTTP-сервер уже имеет `stack_size=12288`.
- **Затирание старой недели** → намеренно, `sz != sizeof(...)` вернёт «нет данных» (`gas_correction_nvs_store.cpp:113`), история начнётся с нуля.
- **Изменение `GasDailyBlob` ломает тесты** → `test/test_gas_daily_tracking.cpp` (проверки `DAILY_SLOTS-1`, `sizeof`) и `test/test_gas_integration.cpp` (JSON `daily`) обновляются вместе с кодом.

## Migration Plan

1. Новые структуры и ключи NVS добавляются рядом со старыми; старый ключ `daily` больше не читается (или читается, но игнорируется).
2. Откат: старые прошивки не знают новых ключей и продолжают использовать прежний 8-дневный blob — новые данные для них просто отсутствуют, старые недельные данные остаются в старом ключе нетронутыми (если его не перезаписывать). Полный даунгрейд безопасен.

## Open Questions

- Кадрирование `pollGasHistory()`: 10 с (как `pollStats`) или реже (60 с)? Данные меняются раз в час/сутки, поэтому 60 с достаточно; итоговое значение уточним при реализации.
- Нужен ли «пропуск» нулевых баров по горизонтали (DeepSeek показывает только дни с активностью) или всегда полная шкала (все часы/дни)? По умолчанию — полная шкала с нулями, что соответствует spec-сценариям.
