## Why

Релизный процесс не разделяет стабильные и тестовые сборки и не гарантирует, что стабильный тег указывает на влитый в `master` код. В результате v0.8.0 был выпущен с невлитой ветки (пришлось force-переносить тег), тестовые сборки предлагались устройствам как обычные, GitHub Pages не обновлялся после тега, а веб-установщик выбирал версию по дате публикации, а не по версии. Дополнительно: контрольная сумма OTA-образа не проверяется — `versions.json` не содержит `sha256`, хотя код проверки в прошивке уже есть.

## What Changes

- **Каналы релизов.** Вводится соглашение: `vX.Y.Z` — стабильный релиз, `vX.Y.Z-rcN` — тестовый (release candidate). Тестовый бакет один; других суффиксов нет. Тег с суффиксом `-rcN` создаёт GitHub Release с флагом prerelease; стабильный — с флагом latest.
- **Guard стабильного тега.** Job релиза проверяет `git merge-base --is-ancestor <tag> origin/master`; тег на недостижимом из `master` коммите валит CI. Стабильную метку нельзя поставить на невлитую ветку.
- **Промоушен rc → stable после merge.** PR может опубликовать только `vX.Y.Z-rcN`. После merge PR отдельный workflow находит старший rc-тег, достижимый из head PR, создаёт аннотированный stable-тег `vX.Y.Z` на merge-коммите (копируя аннотацию rc) и запускает релизный прогон через `workflow_dispatch` (без секретов). Если stable-тег уже существует — не перезатирается; если rc не было — автоматика молчит, остаётся ручной stable-путь. После успешного создания стабильного релиза rc-релиз и тег удаляются.
- **Pages на тегах.** `deploy-pages` запускается и на тегах `v*` после `firmware-build`, наполняя `site/firmware/<tag>/` из артефакта только что собранной прошивки (без гонки с созданием релиза) и пересобирая весь сайт (деплой Pages атомарный).
- **Notes из аннотации тега.** Релиз создаётся с `--notes-from-tag`; `--generate-notes` — только fallback при пустой аннотации. Аннотация тега становится единственным источником changelog.
- **SHA256 в каталоге.** В `versions.json` у каждой версии появляется поле `sha256` (хэш `esp-ot-gateway.bin`). Прошивки с прежней версией кода находят его спящим `lookup_sha256` и начинают проверять целостность OTA-образа — без перепрошивки устройства.
- **Порядок каталога.** `versions.json` сортируется: стабильные сверху (semver по убыванию), затем тестовые. Старые устройства, рендерящие каталог дословно, получают корректный порядок без обновления прошивки.
- **Веб-установщик.** Версии сортируются по semver; по умолчанию выбирается высшая стабильная (или релиз с флагом latest), а не первая из GitHub API. Перед выбором проверяется наличие `manifest.json` с откатом на предыдущую стабильную. Тестовые версии выносятся в отдельную секцию и доступны по deep-link `flasher.html?tag=<tag>`; они никогда не выбираются автоматически.
- **OTA-вкладка устройства (будущая прошивка).** Тестовые версии группируются отдельно («Тестовые»), требуют явного выбора с предупреждением «на свой страх и риск»; старые устройства продолжают видеть их по суффиксу `-rcN` в теге.

## Capabilities

### New Capabilities

- `release-pipeline`: CI-процесс публикации — каналы стабильный/rc, guard достижимости тега из `master`, автоматический промоушен rc → stable на merge (тег на merge-коммите, копирование аннотации, уборка rc), prerelease/latest флаги, публикация Pages на тегах, notes из аннотации тега, вычисление sha256.
- `version-catalog`: артефакт `versions.json` — состав, порядок (stable-first), поля `prerelease` и `sha256`, контракт потребления устройством.
- `ota-update`: устройство — эндпоинт `/api/ota/versions`, отображение каталога (стабильные + бакет тестовых), проверка `sha256` при загрузке OTA-образа.
- `web-flasher`: браузерный установщик — выбор и сортировка версий по semver, дефолт (стабильная/latest), секция тестовых версий, deep-link по тегу, fallback при отсутствии манифеста.

## Impact

- `.github/workflows/tests.yml` — guard, каналы, `--prerelease`/`--latest`, `--notes-from-tag`, sha256, `deploy-pages` на тегах, зависимости job'ов, input `source_rc` и уборка rc.
- `.github/workflows/promote.yml` — новый workflow промоушена rc → stable на `pull_request: closed` (merged).
- `web-flasher/app.js`, `web-flasher/index.html` — semver-сортировка, дефолт, секция тестовых версий, deep-link, проверка манифеста.
- `main/infrastructure/driving/web_page.h` — группировка тестовых версий в выпадашке OTA (ретроактивно работает на старых через суффикс тега).
- `main/infrastructure/driven/ota_version_index_adapter.cpp` — без изменений (URL прежний), но контракт `versions.json` дополняется `sha256`.
- `main/infrastructure/driving/http_controller_adapter.cpp`, `main/infrastructure/driving/ota_interactor.cpp` — оживление проверки `sha256` (существующий код, без новых полей протокола).
- `docs/ota-testing.md` — тестовый тег через `-rcN`, публикация на Pages штатным тег-раном вместо `gh workflow run --ref master`.
- Совместимость: формат `versions.json` расширяется аддитивно; `sha256` активирует проверку на всех устройствах — требуется корректный хэш из CI.
