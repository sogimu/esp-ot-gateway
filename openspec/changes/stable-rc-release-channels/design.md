## Context

Весь релизный контур живёт в одном воркфлоу `.github/workflows/tests.yml` (jobs `test`, `coverage`, `firmware-build`, `deploy-pages`). Текущее состояние:

- `firmware-build` на тег `v*` создаёт GitHub Release (`tests.yml:78-97`) без проверок и без учёта канала; `--generate-notes` фиксирует только влитые на момент тега PR, а для уже существующего релиза notes не трогаются.
- `deploy-pages` (`tests.yml:106-174`) выполняется только при `github.ref == refs/heads/master`, собирает `site/versions.json` из всех релизов и копирует `.bin` всех тегов в `site/firmware/<tag>/`; на тег-ранах пропускается.
- `versions.json` имеет формат `{versions:[{tag,name,published_at,prerelease}]}` и потребляется только прошивкой через `OtaVersionIndexAdapter` → `/api/ota/versions` → `web_page.h:1700-1706`; рендерятся только `tag`, без фильтра и сортировки.
- В прошивке уже есть **спящая** проверка целостности: `OtaInteractor::lookup_sha256()` (`ota_interactor.cpp:59-79`) ищет `"sha256":"…"` в кэше `versions.json`, а `handler_ota_upload` (`http_controller_adapter.cpp:737-751`) включает mbedtls-верификацию, если хэш найден. CI поле не кладёт → `verify` всегда `false`.
- Веб-установщик `web-flasher/app.js` берёт список из GitHub REST API (`app.js:80-114`), авто-выбирает первый не-prerelease в порядке ответа (по дате) и не проверяет наличие `manifest.json`.
- Тестовый канал де-факто — prerelease-теги, которые попадают в `versions.json` и видны устройству; тест bad-image в `docs/ota-testing.md` требует ручного `gh workflow run tests.yml --ref master`, чтобы прогнать Pages.

Ограничение, определяющее дизайн: прошивку на уже развёрнутых устройствах менять нельзя «задним числом». Всё, что должно подействовать на существующие устройства, обязано быть серверной правкой (`versions.json`), а не изменением `web_page.h`.

## Goals / Non-Goals

**Goals:**
- Гарантировать, что стабильный тег `vX.Y.Z` указывает только на коммит, достижимый из `master`.
- Ввести единый тестовый канал `vX.Y.Z-rcN` (один бакет), публикуемый как prerelease, но доступный устройству и веб-установщику.
- Обновлять Pages сразу на теге, без ожидания пуша в `master` и без гонки с созданием релиза.
- Оживить проверку `sha256` OTA-образа на всех устройствах через серверную правку каталога.
- Упорядочить каталог (стабильные сверху) и выбор версии в веб-установщике (semver, дефолт — высшая стабильная, fallback при 404).
- Сделать changelog осмысленным: notes из аннотации тега.

**Non-Goals:**
- Изменение механики A/B-обновления, отката и валидации (`OtaValidityAdapter`, `CrashDiagnosticsAdapter`) — не затрагивается.
- Миграция старых релизов/тегов — остаются как есть.
- Подписывание образов (secure boot / ECDSA) — только контроль целостности `sha256`.
- Смена источника списка в веб-установщике на `versions.json` (см. Open Questions).
- Разделение alpha/beta/rc — бакет тестовых один, суффикс только `-rcN`.

## Decisions

### D1. Каналы: `vX.Y.Z` = stable, `vX.Y.Z-rcN` = test
Соглашение о теге — единственный источник правды о канале. Регэкспы:
- stable: `^v[0-9]+\.[0-9]+\.[0-9]+$`
- test: `^v[0-9]+\.[0-9]+\.[0-9]+-rc[0-9]+$`

Альтернатива: отдельное поле/метка в релизе или бакеты alpha/beta/rc — отклонено, усложняет без пользы; суффикс тега виден даже старой прошивке (она рендерит `tag` дословно).

### D2. Guard только для стабильного тега
Проверка `git merge-base --is-ancestor "$TAG" origin/master` выполняется **только** для stable-тегов. Для `-rcN` guard не применяется — тестовую сборку нужно уметь выпускать с feature-ветки (bad-image тест). Именно это чинит проблему 1, не ломая канал тестирования.

### D3. Флаги релиза
- stable: `gh release create "$TAG" … --latest`, notes — из аннотации тега (fallback `--generate-notes` при пустой аннотации).
- test: `gh release create "$TAG" … --prerelease`, notes — из аннотации тега (prerelease не становится latest автоматически).
- Аннотация передаётся файлом (`--notes-file`): `--notes-from-tag` нельзя комбинировать с `--repo` — gh читает её из локального репозитория (проверено на реальном прогоне).
- Перед извлечением аннотации делается `git fetch --force origin "+refs/tags/$TAG:refs/tags/$TAG"`: `actions/checkout` при checkout тега перезаписывает локальный ref на коммит, и без этого `%(contents)` вернул бы message коммита вместо аннотации (проверено на реальном прогоне).
- существующий релиз: только `gh release upload --clobber` (как сейчас), notes не перегенерируются.

Определение пустой аннотации: `git for-each-ref "refs/tags/$TAG" --format='%(contents)'`; пусто или совпадает с именем тега → `--generate-notes`.

### D4. `deploy-pages` на тегах без гонки
- Условие job: `github.ref == 'refs/heads/master' || startsWith(github.ref, 'refs/tags/v')`.
- `needs: [test, coverage, firmware-build]` — на теге нужен артефакт только что собранной прошивки. `test`/`coverage` на тегах остаются (нужны для `/coverage/` в пересобираемом сайте; см. Open Questions).
- `firmware-build` публикует артефакт `firmware-binaries` (`*.bin`), доступный обоим путям.
- Сборка сайта (деплой Pages атомарный — публикуется весь сайт целиком):
  - текущий тег-ран: `site/firmware/<tag>/` наполняется **из артефакта**, `manifest.json` и `sha256` считаются из артефакта;
  - остальные теги: как сейчас — `gh release download`.
- Корень сайта (`web-flasher/`) на тег-ране берётся из `master` (checkout `ref: master`), а из тега — только `site/firmware/<tag>/`: rc-тег с feature-ветки не должен публиковать код ветки в прод-фронтенд.
- `versions.json` пересобирается целиком на каждом деплое (master и тег) из списка релизов + хэшей.

### D5. `versions.json`: + `sha256`, stable-first порядок
Формат (аддитивно к текущему):
```json
{
  "versions": [
    {"tag":"v0.8.0","name":"…","published_at":"…","prerelease":false,"sha256":"<64 hex>"},
    {"tag":"v0.9.0-rc1","name":"…","published_at":"…","prerelease":true,"sha256":"<64 hex>"}
  ]
}
```
- `sha256` считается в `deploy-pages` от того самого `esp-ot-gateway.bin`, который кладётся на Pages (для текущего тега — от артефакта). Единый источник: хэшируем ровно то, что раздаём.
- Порядок: сначала `prerelease:false` (semver по убыванию), затем `prerelease:true` (semver по убыванию). Реализация — два прохода `sort -V -r` по группам (GNU coreutils на `ubuntu-latest`); кросс-групповое сравнение не нужно.
- `lookup_sha256` старой прошивки ищет `"sha256":"` после `"tag":"<tag>"` — поле кладём в тот же объект, порядок полей сохраняем (`tag` раньше `sha256`). Строковый поиск устойчив, пока `tag` уникален.
- Сериализация строго компактная (`jq -c`, без пробелов после `:` и `,`): прошивка ищет подстроки без пробелов, pretty-print молча ломает проверку на всех устройствах. В CI добавлен assertion на компактность.
- Записи без розданного `.bin` в каталог не попадают вовсе: старый substring-поиск `sha256` не ограничен объектом и у версии без хэша вернул бы хэш следующей записи.
- Лимит тела на устройстве `MAX_BODY_SIZE = 64 КиБ` (`ota_version_index_adapter.cpp:20`) — 20 версий с хэшами ≈ несколько КиБ, запас большой.

### D6. Устройство: группировка тестовых (новая прошивка), ретроактивность (старая)
- Старая прошивка не меняется: рендерит все теги в порядке массива; за счёт D5 стабильные сверху, тестовые помечены суффиксом `-rcN`. Тестирование OTA на старых устройствах сохраняется.
- Новая прошивка: если элемент — объект с `prerelease:true`, тег идёт в `<optgroup label="Тестовые">` под стабильными; при выборе тестового показывается предупреждение, `otaStart()` требует `confirm()`. Серверной фильтрации нет — каталог единый.
- Проверка `sha256` в `handler_ota_upload` уже реализована; правок кода не требуется, включается наличием поля. Явно покрываем тестом (host) `lookup_sha256` на новом формате.

### D7. Веб-установщик: semver-сортировка, дефолт, тестовая секция, fallback
- Список из GitHub API (источник сохраняем, см. Open Questions) сортируется клиентским semver-компаратором по убыванию; prerelease идут после стабильных.
- Дефолт = высшая **стабильная** по semver (детерминированно, не зависит от флага latest и даты публикации). Дополнительно stable-релизы создаются с `--latest`, чтобы GitHub UI совпадал.
- Тестовые версии — в `<optgroup label="Тестовые (на свой риск)">`; авто-выбор их не выбирает.
- Deep-link `flasher.html?tag=<tag>`: `URLSearchParams`; если тег найден — выбирается (включая тестовый), авто-дефолт отключается; если не найден — дефолт.
- Перед активацией прошивки — `HEAD firmware/<tag>/manifest.json`; при 404 показывается сообщение и (для авто-выбора) откат к следующей стабильной по убыванию. Защита от «дефолт падает с 404».

### D8. Notes — из аннотации тега
Аннотация тега объявляется единственным источником changelog; при создании релиза она передаётся файлом (`--notes-file`), т.к. `--notes-from-tag` несовместим с `--repo`. `--generate-notes` — только fallback при пустой аннотации. Гибрид (авто-список PR + аннотация) отклонён как дублирующий: для v0.8.0 аннотация содержательнее авто-списка (только PR #52).

### D9. Тестовый канал bad-image
`docs/ota-testing.md` переводится на:
- тег `vX.Y.Z-rcN` с throwaway-ветки (guard не применяется к rc);
- штатный тег-ран `firmware-build` + `deploy-pages` публикует образ на Pages сразу;
- устройство видит тег в каталоге (старые — по суффиксу, новые — в бакете «Тестовые»).
Ручной `gh workflow run tests.yml --ref master` больше не нужен.

### D10. Промоушен rc → stable: отдельный workflow и цель тега
- Новый workflow `.github/workflows/promote.yml`, триггер `pull_request: types: [closed]`, условие `merged == true && base.ref == 'master'`. Отдельный файл, а не доп. триггер в `tests.yml`, чтобы на закрытии PR не гонять `test`/`coverage`/`firmware-build`.
- Явный checkout базовой ветки (`ref: master`, `fetch-depth: 0`, `fetch-tags: true`): нужны полный граф и теги; на closed-событии дефолтный checkout может указывать на merge-ref.
- Stable-тег ставится на `github.event.pull_request.merge_commit_sha` — коммит слияния в master. Это устойчиво к squash/rebase (rc-коммит может не быть предком) и включает параллельные изменения master. Альтернатива «буквально переименовать rc-тег на rc-коммите» отклонена.
- Permissions job: `contents: write`, `actions: write`.

### D11. Поиск rc и выбор версии
- `git tag --merged "$HEAD_SHA" -l 'v[0-9]*.[0-9]*.[0-9]*-rc[0-9]*'` (HEAD_SHA = `pull_request.head.sha`), затем строгий регэксп и старший по `sort -V | tail -1`.
- HEAD_SHA доступен локально при merge-коммитах (он предок master). При будущем переходе на squash/rebase коммит может отсутствовать — fallback: искать rc-теги, достижимые из master (`merge-base --is-ancestor`), или через GitHub API (см. Risks).
- Stable-имя: `${rc%-rc[0-9]*}` → `vX.Y.Z`.
- Если rc не найдено — job завершается успешно, ничего не создаётся (ручной stable-путь остаётся: пуш `vX.Y.Z` на master идёт по обычному guard+release).
- Если тег/релиз `vX.Y.Z` уже существует — не перезатираем, пропускаем (идемпотентность).
- Несколько rc — берём старший по semver.
- Если `vX.Y.Z` не выше текущей максимальной стабильной — пишем `::warning::` (не блокируем: легитимные патч-релизы, как v0.7.1 после v0.8.0, должны проходить).

### D12. Цепочка без секретов
- Тег, созданный `GITHUB_TOKEN`, не триггерит `push: tags` (антирекурсия GitHub). Поэтому после пуша stable-тега promotion вызывает `gh workflow run tests.yml --ref "$STABLE" -f source_rc="$RC"`.
- `workflow_dispatch` — документированное исключение: запускается даже от `GITHUB_TOKEN`; требует permission `actions: write`.
- В `tests.yml` добавляется input `source_rc` (пустой по умолчанию), чтобы релизный прогон знал, какой rc удалить.
- Альтернативы (PAT/App-токен, «всё в одном job») отклонены: секреты / лишний рефакторинг.

### D13. Аннотация и уборка rc
- Notes stable-релиза = аннотация rc-тега: `git for-each-ref "refs/tags/$RC" --format='%(contents)'` копируется в новый аннотированный тег. Changelog пишется один раз при выпуске rc.
- Если аннотация rc пуста — stable-тег также без аннотации, релизный прогон уйдёт в `--generate-notes`.
- Уборка rc выполняется в релизном прогоне (`tests.yml`) **только после** успешного создания stable-релиза (ветка «Creating new release») по `source_rc`: `gh release delete "$RC" --yes` + `git push origin ":refs/tags/$RC"`. При ветке «release exists»/пропуске — не удаляем.
- `deploy-pages` зависит от `firmware-build`, поэтому в том же прогоне каталог уже не содержит rc.

## Risks / Trade-offs

- **Оживление `sha256` отклоняет несовпавший образ** → если CI положит неверный/устаревший хэш, OTA сломается. Митигация: хэшируем ровно раздаваемый файл в одном job; первичная обкатка на `-rcN`; при откате — вернуть каталог без `sha256` (проверка снова выключится, деградация безопасная).
- **Полная пересборка сайта на каждый тег** → медленнее (скачивание всех прошлых `.bin`), но деплой Pages атомарный, иначе нельзя. Митигация: идемпотентность, кэш не требуется.
- **`test`/`coverage` на тег-ранах дублируют прогон merge-коммита** → трата минут CI. Митигация: оставлены ради `/coverage/` в тег-деплое; при желании вынести в Open Question.
- **Guard только для stable** → можно выпустить rc «откуда угодно»; это осознанно (тестовый канал), стабильную метку так поставить нельзя.
- **Веб-установщик зависит от GitHub API (rate limit 60/ч на IP)** → при исчерпании список не загрузится. Митигация: возможный переход на `versions.json` (Open Question), пока — обработка ошибки.
- **`sort -V` — не полный semver** → но группы однородны (bare semver / все с `-rcN`), внутри группы сравнение корректно.
- **Старые устройства не показывают группировку** → тестовые видны в общем списке; метка — суффикс `-rcN`, порядок стабильные сверху. Приемлемо (тестирование на старых — обязательное требование).
- **Fork PR и read-only токен** → на `pull_request: closed` для PR из форка `GITHUB_TOKEN` может быть read-only, и promotion не создаст тег. Свои ветки (`sogimu/*`) не затронуты; при появлении форков — перейти на sweep по `push: branches: [master]`.
- **HEAD_SHA недоступен при squash/rebase** → `git tag --merged "$HEAD_SHA"` упадёт; митигация: fallback на rc-теги, достижимые из master, либо GitHub API. Проект использует merge-коммиты, так что риск отложенный.
- **Повторный merge / повторный прогон** → promotion идемпотентен: существующий stable-тег/релиз не перезатирается, rc не удаляется.
- **Пустая аннотация rc** → stable-релиз уйдёт в `--generate-notes` (fallback D8).

## Migration Plan

1. Правки `tests.yml`, `promote.yml` и `app.js` вливаются в `master`; следующий `deploy-pages` на master пересоберёт `versions.json` с `sha256` — проверка включается на всех устройствах.
2. Первый merge PR с `-rcN` обкатывает промоушен: stable-тег на merge-коммите, `workflow_dispatch`, релиз, уборка rc.
3. Откат: revert воркфлоу/`app.js`. `versions.json` без `sha256` → верификация выключается; тег-раны перестают деплоить Pages, промоушен не запускается — работа возвращается к master-only. Данные и прошивки не мигрируются.

## Open Questions

- Оставлять ли `test`/`coverage` на тег-ранах (нужны только ради `/coverage/`), или деплоить на теге без coverage-артефакта, а coverage обновлять следующим master-раном?
- Перевести ли список веб-установщика с GitHub API на same-origin `versions.json` (нет rate limit, единый источник с устройством), оставив notes через API как опциональное обогащение?
