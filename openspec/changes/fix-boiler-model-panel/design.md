## Context

Панель «Модель котла» (`web_page.h:395–428`) позволяет редактировать `gas_temp_offset`, пары `ch_pmin/ch_pmax`, `dhw_pmin/dhw_pmax` и три точки кривой КПД, а кнопка отправляет всё в `POST /api/control`. В действительности:

- `handler_control()` (`http_controller_adapter.cpp:128–193`) парсит только `ch_enable`, `ch_mode`, `dhw_enable`, `ch/dhw_setpoint`, `dhw_hysteresis`, `tz_offset`, `pid_*`, `fault_reset`, `reset_*`, `k_calib`, `gas_meter_base`, `gas_meter_correct`. Поля модели не читаются — `IGasCalibration::set_ch_power/set_dhw_power/set_gas_temp_offset/set_efficiency_points` не вызываются ниоткуда (проверено grep по `main/` и `git log -S` по HTTP-адаптеру — не было никогда).
- `pollStats()` выполняется каждые 10 с (при открытой вкладке «Статистика»/«Счётчик газа») и в строках 1406–1417 безусловно перезаписывает все `mf_*` поля.
- Кривая КПД — мёртвый конфиг: `efficiency_continuous()` вызывается только из тестов, в `GasFlowService::execute()` не участвует (модель считает расход по входной мощности: `flow = k × P_вход / cv`). Значения 0.98/0.93/0.88 — от неконденсационного котла, поля зажаты `max=1.00`, что для конденсационника с КПД >100% невыразимо.

Инфраструктура dirty-состояния уже есть (`dirtyFields` для `tz`/`sntp`/`mb`, глобальный `dirty` для панелей управления), но к панели модели не подключена.

## Goals / Non-Goals

**Goals:**

- Правки полей модели не затираются опросом до нажатия кнопки применения.
- Кнопка применения реально применяет параметры: HTTP-слой вызывает существующие сеттеры `IGasCalibration`.
- Кривая КПД убрана из панели.
- CH и БКН остаются отдельными парами полей (вариант A, выбран заказчиком).

**Non-Goals:**

- Удаление мёртвого бэкенд-кода КПД (`eff_*` в state/NVS-blob, `efficiency_continuous()`, `set_efficiency_points`, `gas_correction_interactor`): формат `NvsBoilerCalBlob`/`NvsEffBlob` не трогаем, чтобы не потерять настройки модели при апгрейде.
- Смена дефолтов 5.5/24 → 3.5/24.7 для Baxi Duo-tec Compact 1.24.
- Ускорение сходимости `k_calib` (фильтр Калмана `Q=0.02`).

## Decisions

### 1. Применение параметров через существующий `POST /api/control`

Добавляем в `handler_control()` разбор пяти полей и вызовы уже готовых сеттеров:

```
gas_temp_offset                         → gas_->set_gas_temp_offset(f)
ch_pmin + ch_pmax (оба присутствуют)    → gas_->set_ch_power(pmin, pmax)
dhw_pmin + dhw_pmax (оба присутствуют)  → gas_->set_dhw_power(pmin, pmax)
```

Клампинг/валидация остаются внутри сеттеров (`set_ch_power`: 1…15 / 10…40, при `pmin ≥ pmax` — откат на 5.5/24; `set_gas_temp_offset`: −20…10). Отсутствие поля определяем по существующему сентинелу `json_get_float() == -1e38f`.

**Альтернативы:** отдельный эндпоинт `/api/model` — отклонён: плодит маршруты и дублирует парсинг, тогда как все прочие настройки уже идут через `/api/control`. Передача коэффициентов напрямую в state из HTTP — отклонён: обходит валидацию и NVS-персистентность сеттеров.

### 2. Sticky dirty-флаг `dirtyFields.model` для полей модели

Поля `mf_*` при `oninput`/`onfocus` выставляют `dirtyFields.model = true`; блок 1406–1417 в `pollStats()` оборачивается в `if(!dirtyFields.model)`. Флаг сбрасывается только по успешному ответу на применение. Визуально поле можно подсветить так же, как `setDirtyField()` подсвечивает `mb`/`tz`.

**Альтернативы:** per-field `onfocus`/`onblur` как у `tz`/`mb` — отклонён: blur снимает флаг до нажатия «Применить», и опрос успевает затереть значение в зазоре. Глобальный `dirty` как у `applyControl` — отклонён: он гасит обновление всей панели управления (`poll()`, строка 1071), сбрасывается чужими кнопками и создаёт связность между вкладками.

### 3. Вариант A: две независимые пары CH/DHW

Оставляем `ch_pmin/ch_pmax` и `dhw_pmin/dhw_pmax` раздельными. Хотя у одноконтурного Duo-tec Compact 1.24 + БКН диапазон один и тот же (3.5–24.7 кВт вход), раздельные пары не мешают и покрывают случай двухконтурного котла без переделки UI.

**Альтернатива:** одна пара с зеркалированием в обе пары при сохранении — отклонена заказчиком.

### 4. Кривая КПД удаляется только из UI

Удаляем три `info-row` (строки 409–418), строки заполнения `eff_*` из `pollStats` (1412–1417) и `eff_*` из payload. Бэкенд не трогаем: `/api/stats` продолжит отдавать `eff_*`, но фронт их игнорирует.

**Альтернатива:** полное удаление сквозь state/NVS/API — отклонено из-за смены `sizeof` NVS-blob: существующая логика отбрасывает blob при несовпадении размера, что обнулило бы пользовательские настройки модели.

### 5. Буфер тела запроса оставляем `body[256]`

Payload модели с пятью полями — ~120 байт (после удаления `eff_*`), укладывается с запасом. Добавление новых полей в `/api/control` в будущем требует проверки размера.

## Risks / Trade-offs

- **[Поля остаются «грязными» навсегда, если пользователь ушёл без применения]** → Пока флаг стоит, поля не обновляются; перезагрузка страницы сбрасывает состояние и подтягивает сохранённые значения. Приемлемо: пользователь видит свои правки, а не молча затёртые.
- **[`handler_control` отвечает `{"ok":true}` даже когда сеттер отклонил значение]** → Клампы сеттеров могут изменить значение молча. Митигация: после успешного применения dirty-флаг снимается, и ближайший опрос (≤10 с) подтягивает фактически сохранённые значения в поля.
- **[Удаление `eff_*` из payload при живом бэкенде]** → Кнопка больше не перезаписывает КПД; дефолты в NVS остаются. Не влияет на расход газа, т.к. КПД не участвует в расчёте.
- **[HTTP-слой не покрыт тестами]** → Проверка сборкой и ручным сценарием (изменить поле, дождаться опроса, нажать «Применить», проверить `/api/stats` и NVS после перезагрузки).

## Migration Plan

Изменение только фронтенд + один обработчик; формат NVS не меняется. Откат — возврат прежнего `web_page.h` и `http_controller_adapter.cpp`. После прошивки пользователь вручную вводит паспортные 3.5/24.7 через починенную панель.
